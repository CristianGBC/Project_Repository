# Auditoría de consistencia distribuida · Fase 7.5

## Actualización de la Fase 7.6

La carrera descrita en la auditoría original está corregida. El borrado
cancela versiones pendientes o fallidas bajo el lock del documento. La
cancelación persiste después de restaurar y ambos publicadores la comprueban.
Los archivos y referencias se conservan. El control optimista sustituye la
última escritura sobre el mismo campo entre formularios que comparten una
revisión. El versionamiento del archivo mantiene sus bloqueos pesimistas.
Las lecturas académicas entre escuelas son intencionales para usuarios
autenticados y documentos publicados. [Política actual](frontend-final-integration.md).

| Comportamiento | Garantía y evidencia | Pruebas y límites |
|---|---|---|
| Detección y recuperación | `health_monitor.py`, `run` y `check_cycle` esperan un ciclo completo, incluidas las escrituras, y después el intervalo. Las sondas HTTP se lanzan con `asyncio.gather`. `node_health.py:probe_node` aplica el timeout HTTP y verifica servicio, ID y respuesta. `_persist_observations` mantiene contadores consecutivos por nodo, actualiza `last_seen_at` en cada éxito y `health_changed_at` al cambiar `health`. | `test_health_monitor.py` cubre concurrencia, timeouts, umbrales, recuperación y reinicios. Los contadores se reinician con el proceso. Con 5 s, timeout nominal 2 s y ciclos uniformes, tres fallos inmediatos tardan aproximadamente 10–15 s y tres fallos por timeout 16–21 s, medidos desde un fallo antes de una sonda o durante la espera entre ciclos. Dos éxitos rápidos tardan aproximadamente 5–10 s. La latencia del ciclo, SQL y la semántica de timeout por operación HTTP pueden ampliar esas cifras. |
| Eliminación y restauración | `document_service.py:soft_delete_document` y `restore_document` bloquean la fila y cambian las marcas en PostgreSQL. Los archivos, versiones y réplicas se conservan. `_specific_version_record` y `_catalog_record` comprueban el borrado, también para rutas directas. Recuperar un nodo no quita la marca. | `test_soft_delete_restricts_reads_and_restore_preserves_versions_and_files`. Restaurar no reconstruye archivos ni comprueba RF de forma síncrona. Una descarga iniciada antes del borrado puede continuar. `test_historical_version_of_soft_deleted_document_repairs_independently` confirma que reparación puede tratar versiones históricas de documentos borrados. |
| Publicación concurrente | `_create_pending_version` bloquea el documento antes de reservar MAX+1. El modelo impone UNIQUE(document_id, version_number). `_finalize_replicated_version` bloquea el documento y las réplicas, exige el RF en hosts distintos y solo mueve el puntero hacia un número mayor. Si termina 3 antes que 2, el puntero permanece en 3. | `test_concurrent_version_uploads_get_unique_monotonic_numbers` y `test_concurrent_rf3_versions_remain_unique_and_fully_replicated`. El finalizador normal no vuelve a exigir `deleted_at IS NULL`. Una subida ya iniciada puede publicar una versión interna y avanzar el puntero tras el borrado. La marca permanece y las lecturas académicas lo excluyen. Falta una prueba dedicada para esta carrera. |
| Reconciliación | `upload_reconciliation.py` usa locks advisory por versión y locks de fila en transacciones de publicación. Comprueba el borrado al tomar el trabajo y al publicar, exige copias verificadas en hosts distintos y protege el puntero ante una versión más nueva. | `test_two_reconcilers_cannot_process_same_version_concurrently`, `test_soft_deleted_document_cancels_job_without_publication` y `test_recovered_old_version_never_replaces_newer_current_version`. Una transferencia ya iniciada puede dejar bytes a recuperar o auditar. |
| Metadatos | `api/documents.py:update_document_metadata` aplica el PATCH bajo lock de fila y revalida el borrado. | Las escrituras se serializan. Para el mismo campo prevalece la última escritura. No se ofrece ETag ni control optimista. |
| Déficit y exceso | `replication_diagnostics.py:find_replication_deficits` cuenta `healthy` por catálogo. El cálculo operativo añade nodo y host habilitados y nodo distinto de DOWN. UNKNOWN puede contar para ese cálculo. `replica_repair.py:_plan_action` prioriza el origen y considera limpieza si la opción está habilitada y el RF accesible tiene excedente. | `test_monitor_does_not_change_replicas_and_diagnoses_operational_deficit`, `test_recovery_never_changes_missing_or_corrupted_replicas`, `test_recovered_origin_is_retained_and_excess_is_safely_removed`. Cuatro copias para RF=3 pueden permanecer con limpieza deshabilitada. El estado operativo es una estimación del catálogo. |
| Eliminación física y objetos huérfanos | `replica_repair.py:_cleanup_replica` protege el origen y verifica que queden suficientes alternativas catalogadas en hosts distintos antes del DELETE interno. El nodo valida el SHA esperado. `storage/document_store.py` usa claims y limpieza de temporales cuando controla el fallo. | El DELETE HTTP y la actualización SQL son pasos separados. Una caída entre ellos puede dejar catálogo y disco divergentes. Las alternativas se evalúan con estados del catálogo. `verified_at` indica la última verificación registrada, no una lectura actual. Los archivos de documentos borrados que conservan referencias no son huérfanos. No hay inventario físico global en el dashboard. |

Mejoras a evaluar en 7.6 o posteriormente: prueba de borrado durante publicación normal y decisión explícita sobre cancelación, control optimista de edición, comprobación de autorización por escuela en rutas académicas directas y auditoría de discrepancias de almacenamiento. La descarga de versión invoca el servicio desde una ruta autenticada sin pasar identidad de escuela al método; conviene verificar el alcance de lectura con pruebas específicas. Este trabajo de observación conserva el comportamiento actual.
